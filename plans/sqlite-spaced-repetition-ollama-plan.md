## Goal

Add a Mnemosyne-like spaced repetition system to the Obsidian plugin without modifying notes during review.

The plugin should be able to:

- Generate review questions from a note using a local Ollama model.
- Store review state in a separate SQLite database.
- Show due cards from across the vault.
- Let the user grade recognition with `0, 1, 2, 3, 4`.
- Treat grade `0` as "not remembered; show again after a few other cards today".
- Support multiple question answer styles: multiple choice, exact typed answer, LLM-checked typed answer, and self-check answer.
- Keep chats with a note and generated learning items linked to the source note.

## Best Shape

Use an autogenerated review database, not autogenerated notes.

Notes should remain the source material. The spaced repetition database should own generated questions, review history, scheduling state, LLM chats, and metadata. This avoids the main problem with Obsidian Spaced Repetition: review metadata getting written back into notes.

The plugin can optionally create a small link/reference section in a note later, but that should be opt-in. The first implementation should not modify the source note at all.

## Multi-Note Study Entities

Some useful questions should come from several related notes, not one note.

Examples:

- Compare concepts across two notes.
- Ask synthesis questions over a topic folder.
- Use one note as theory and another as code/example.
- Generate questions from a group of notes that share a tag.
- Review a project/module as one knowledge unit.

Treat this as a first-class entity called a `study_set`.

A `study_set` is a saved group of notes and optional selection rules. Questions can belong either to one source note or to a study set. This avoids pretending every generated question has exactly one source note.

Recommended source types:

- `manual`: user picks notes/files directly.
- `tag`: all notes with a selected tag.
- `folder`: all notes under a folder.
- `links`: active note plus outgoing linked notes.
- `backlinks`: active note plus notes that link to it.
- `query`: future Dataview-like or plugin-specific query.

The review system should support:

- Questions attached to one note.
- Questions attached to a study set.
- Questions attached to a study set but referencing multiple concrete source notes.

This lets the plugin generate cross-note questions without writing special markers into notes.

Optional note marking can come later:

```text
llm-study-set: Machine Learning Basics
llm-study-tags:
  - spaced-repetition
  - generated
```

For the first implementation, use plugin-managed database state and Obsidian metadata/tags/folders/links as inputs. Avoid requiring special frontmatter until there is a strong reason.

## SQLite Decision

The current `src/database/DatabaseManager.ts` is not SQLite. It is a JSON database stored in `transcripts.db`.

For real SQLite inside an Obsidian plugin, use `sql.js` first:

- It is WASM-based and works in browser-like plugin environments.
- It avoids native Node module packaging problems.
- It can persist a `.sqlite` file through Obsidian's vault adapter.
- It has a better chance of working across desktop and mobile than `better-sqlite3`.

Avoid `better-sqlite3` for the initial version unless this plugin is intentionally desktop-only. Native modules in Obsidian plugins are painful to build, publish, and load reliably.

Proposed database path:

```text
.obsidian/plugins/gpt4free-text-generator-plugin/spaced-repetition.sqlite
```

Alternative if we want vault-visible backups:

```text
LLM Automation/spaced-repetition.sqlite
```

Recommendation: keep it in the plugin directory first, beside `data.json` and `transcripts.db`, and add it to `.gitignore`.

## Main User Workflows

### Generate Questions From Current Note

Command:

```text
Generate Spaced Repetition Questions From Current Note
```

Flow:

1. Read active note content.
2. Let user choose number of questions, answer styles, target tags, and Ollama model.
3. Ask Ollama for structured JSON questions.
4. Validate and normalize the generated questions.
5. Save them to the SQLite database linked to the note path.
6. Open the note's question list or show a success notice.

### Generate Questions From Related Notes

Command:

```text
Generate Spaced Repetition Questions From Related Notes
```

Flow:

1. Start from active note.
2. Let user choose the related-note source:
   - selected notes
   - outgoing links
   - backlinks
   - tag
   - folder
3. Create or update a `study_set`.
4. Resolve concrete notes for that study set.
5. Build a combined context with source labels.
6. Ask Ollama for questions that can be single-note or cross-note.
7. Save questions under the study set and record concrete source notes in `question_sources`.

Important prompt instruction:

```text
When a question depends on more than one note, say which source notes support the answer.
```

### Review Due Cards

Command:

```text
Open Spaced Repetition Review
```

Flow:

1. Query due questions where `next_repeat_at <= now` or `should_reask = true`.
2. Mix global due cards and today's reask queue.
3. Show one card at a time.
4. User answers depending on question type.
5. User grades recognition as `0, 1, 2, 3, 4`.
6. Scheduler updates `next_repeat_at`, interval, ease, repetition count, lapse count, and review history.
7. Grade `0` puts card into an intra-session reask queue after N other cards.

### Manage Questions For A Note

Command:

```text
Open Spaced Repetition Items For Current Note
```

Flow:

1. Find database note entry by active note path.
2. Show generated questions.
3. Allow enable/disable, edit, delete, regenerate, and force due.
4. Show per-question schedule and history.

### Manage Study Sets

Command:

```text
Open Spaced Repetition Study Sets
```

Flow:

1. List saved study sets.
2. Show source rule, resolved notes, generated questions, due count, and last generated date.
3. Allow refresh notes, regenerate questions, disable set, edit source rule, or delete set.
4. Allow opening a review session scoped to one study set.

### Chat With Current Note

Command:

```text
Chat With Current Note Using Ollama
```

Flow:

1. Read active note.
2. Open chat panel/modal.
3. Send messages to Ollama with note context.
4. Save chat turns to the same SQLite database under the note entry.
5. Allow converting a chat answer into one or more review questions later.

## Proposed Data Model

### notes

One row per Obsidian source note.

```sql
CREATE TABLE notes (
  id TEXT PRIMARY KEY,
  note_path TEXT NOT NULL UNIQUE,
  note_title TEXT NOT NULL,
  content_hash TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  repeat_at TEXT,
  should_reask_global INTEGER NOT NULL DEFAULT 0,
  tags_json TEXT NOT NULL DEFAULT '[]'
);
```

### study_sets

One row per reusable multi-note context.

```sql
CREATE TABLE study_sets (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  description TEXT,
  source_type TEXT NOT NULL,
  source_rule_json TEXT NOT NULL DEFAULT '{}',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  repeat_at TEXT,
  should_reask_global INTEGER NOT NULL DEFAULT 0,
  tags_json TEXT NOT NULL DEFAULT '[]',
  enabled INTEGER NOT NULL DEFAULT 1
);
```

Examples for `source_rule_json`:

```json
{ "type": "manual", "notePaths": ["A.md", "B.md"] }
```

```json
{ "type": "tag", "tags": ["machine-learning"], "includeNestedTags": true }
```

```json
{ "type": "folder", "folderPath": "Notes/ML", "recursive": true }
```

### study_set_notes

Resolved note membership for study sets. This can be refreshed when a set is opened or generated.

```sql
CREATE TABLE study_set_notes (
  study_set_id TEXT NOT NULL REFERENCES study_sets(id) ON DELETE CASCADE,
  note_id TEXT NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  role TEXT,
  added_at TEXT NOT NULL,
  PRIMARY KEY (study_set_id, note_id)
);
```

### questions

One row per generated review item.

```sql
CREATE TABLE questions (
  id TEXT PRIMARY KEY,
  note_id TEXT REFERENCES notes(id) ON DELETE CASCADE,
  study_set_id TEXT REFERENCES study_sets(id) ON DELETE CASCADE,
  question_name TEXT,
  question_text TEXT NOT NULL,
  question_type TEXT NOT NULL,
  answer_text TEXT,
  choices_json TEXT,
  answer_check_mode TEXT NOT NULL DEFAULT 'self',
  metadata_json TEXT NOT NULL DEFAULT '{}',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  next_repeat_at TEXT NOT NULL,
  last_reviewed_at TEXT,
  should_reask INTEGER NOT NULL DEFAULT 0,
  reask_after_count INTEGER NOT NULL DEFAULT 0,
  enabled INTEGER NOT NULL DEFAULT 1
);
```

At least one of `note_id` or `study_set_id` must be present.

### question_sources

Concrete source notes used for a question. This matters for cross-note questions where `study_set_id` is the owner but multiple notes contributed evidence.

```sql
CREATE TABLE question_sources (
  question_id TEXT NOT NULL REFERENCES questions(id) ON DELETE CASCADE,
  note_id TEXT NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  source_label TEXT,
  source_excerpt TEXT,
  PRIMARY KEY (question_id, note_id)
);
```

Question types:

- `multiple_choice`
- `typed_exact`
- `typed_llm_checked`
- `self_check`

Answer check modes:

- `self`
- `exact`
- `llm`

### schedules

Keep scheduling fields separate from the question text so future algorithm changes are easier.

```sql
CREATE TABLE schedules (
  question_id TEXT PRIMARY KEY REFERENCES questions(id) ON DELETE CASCADE,
  algorithm TEXT NOT NULL DEFAULT 'mnemosyne_like_v1',
  interval_days REAL NOT NULL DEFAULT 0,
  ease REAL NOT NULL DEFAULT 2.5,
  repetition_count INTEGER NOT NULL DEFAULT 0,
  lapse_count INTEGER NOT NULL DEFAULT 0,
  last_grade INTEGER,
  due_position INTEGER
);
```

### review_history

Append-only review log.

```sql
CREATE TABLE review_history (
  id TEXT PRIMARY KEY,
  question_id TEXT NOT NULL REFERENCES questions(id) ON DELETE CASCADE,
  reviewed_at TEXT NOT NULL,
  grade INTEGER NOT NULL,
  user_answer TEXT,
  checker_result_json TEXT,
  previous_next_repeat_at TEXT,
  next_repeat_at TEXT,
  elapsed_ms INTEGER
);
```

### note_chats

One row per chat session with a note.

```sql
CREATE TABLE note_chats (
  id TEXT PRIMARY KEY,
  note_id TEXT NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  title TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  metadata_json TEXT NOT NULL DEFAULT '{}'
);
```

### note_chat_messages

One row per chat turn.

```sql
CREATE TABLE note_chat_messages (
  id TEXT PRIMARY KEY,
  chat_id TEXT NOT NULL REFERENCES note_chats(id) ON DELETE CASCADE,
  role TEXT NOT NULL,
  content TEXT NOT NULL,
  created_at TEXT NOT NULL,
  metadata_json TEXT NOT NULL DEFAULT '{}'
);
```

### code_links

Future-facing table for the "code runner" direction.

```sql
CREATE TABLE code_links (
  id TEXT PRIMARY KEY,
  note_id TEXT NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  file_path TEXT NOT NULL,
  language TEXT,
  created_at TEXT NOT NULL,
  metadata_json TEXT NOT NULL DEFAULT '{}'
);
```

## Scheduling Model

Use a Mnemosyne-like grade scale:

- `0`: blackout / not remembered. Reask today after a few other cards.
- `1`: barely recognized. Short interval.
- `2`: partial recall. Short but non-immediate interval.
- `3`: remembered with effort. Normal growth.
- `4`: easy / fluent. Faster growth.

Initial simple algorithm:

```text
grade 0:
  should_reask = true
  reask_after_count = 3
  next_repeat_at = now
  interval_days unchanged or reset to 0

grade 1:
  should_reask = false
  interval_days = 1
  ease -= 0.20

grade 2:
  should_reask = false
  interval_days = max(1, previous_interval * 1.2)
  ease -= 0.05

grade 3:
  should_reask = false
  interval_days = max(2, previous_interval * ease)

grade 4:
  should_reask = false
  interval_days = max(3, previous_interval * (ease + 0.35))
  ease += 0.10
```

Clamp ease between `1.3` and `3.0`.

For new cards:

```text
grade 1 -> tomorrow
grade 2 -> tomorrow
grade 3 -> 3 days
grade 4 -> 5 days
```

The exact intervals can be tuned after the review UI exists. The important behavioral requirement is grade `0`: it should not schedule tomorrow; it should reappear in the same session after several other cards.

## Review Queue Selection

Create `SpacedRepetitionQueueService`.

Responsibilities:

- Select cards due today.
- Include `should_reask = true` cards whose `reask_after_count` has reached zero.
- Decrement `reask_after_count` after each non-reask card.
- Avoid showing two questions from the same note back-to-back when possible.
- Limit session size with a setting such as `maxReviewCardsPerSession`.

Suggested default order:

1. Reask-ready cards.
2. Overdue cards, oldest due date first.
3. New cards if the user enables new cards in the session.

Settings to add:

- `ollamaTextModel`, default user-configurable, likely `gemma3:27b` or whatever local model name is actually installed
- `ollamaTimeout`, default `120000`
- `defaultLLMProvider` should accept `ollama`

Ollama endpoints:

- Generate/chat: `POST /api/chat`
- Model list: `GET /api/tags`

Use Obsidian `requestUrl`, not browser `fetch`, to avoid CORS issues.

For structured question generation, prefer JSON-only prompts and validate the response before saving. Do not trust model JSON blindly.

## Question Generation Prompt Contract

Ask Ollama to return JSON like:

```json
{
  "questions": [
    {
      "questionName": "Short label",
      "questionText": "What is ...?",
      "questionType": "self_check",
      "answerText": "Expected answer",
      "choices": null,
      "answerCheckMode": "self",
      "tags": ["example"],
      "metadata": {
        "sourceQuote": "Optional short quote",
        "difficulty": "medium"
      }
    }
  ]
}
```

Validation rules:

- `questionText` and `answerText` are required.
- `questionType` must be one of the known types.
- Multiple choice questions must have exactly four choices and one correct answer.
- Exact typed answers should include normalized expected answer variants if useful.
- LLM-checked answers need a rubric.
- Reject or repair malformed JSON before writing to SQLite.

## Risks And Open Questions

- `sql.js` WASM bundling needs care in the Obsidian plugin build pipeline.
- The current plugin has an Android build path; confirm whether SQLite/WASM needs to work there too.
- Ollama is local desktop-first. It will not work on mobile unless the phone can reach an Ollama server.
- Generated questions need editing tools because LLM output will sometimes be subtly bad.
- A pure database system is safer for notes, but the database needs backup/export commands.
- Need decide whether review records are stored in plugin directory or vault-visible folder.
- Need decide whether grade `0` should reset long-term ease or only affect same-session reask.
- Need decide whether study sets should be purely database-defined or optionally declared in note frontmatter.
- Need decide how much source text to store in `question_sources`; excerpts are useful, but full duplicated note content would bloat the database.

## Recommendation

Start with Phase 1 and Phase 2 before adding Ollama generation, but include the `study_set` tables from the beginning.

That gives us the thing you actually care about first: Mnemosyne-like repetition with `0` reask behavior, no note mutation, and enough structure for multi-note questions later. Once the scheduler and review loop feel right, Ollama generation becomes a content source rather than the heart of the system.
